# 대화형 일기장 웹앱 — 설계

- 날짜: 2026-11-17
- 상태: 승인됨 (2026-11-17)
- 수준: **MVP / 데모용** (클린 아키텍처·DDD 아님). 범위를 키우지 말 것.

## 1. 의도와 이유

빈 페이지 앞에서 일기를 못 쓰는 사람을 위해, **질문에 답하다 보면 일기가 써지는** 웹 서비스.
앱이 "오늘 하루는 어떠셨나요?"로 시작해 Claude API로 몇 가지를 더 묻고, 그 대화로 일기 초안을 써 준다. 최종 수정은 사람이 한다. 테마와 폰트를 다양하게 골라 꾸밀 수 있다.

**왜 지금:** Agentic Engineering 강의 5회차(2026-12-01) 발표에서 **배포된 서비스가 실제로 돌아가는 모습**을 보여 주는 것이 목표. 동시에 이 프로젝트는 `나만의 AI 하네스 구축 노트`의 하네스(ADR → 스펙 → 티켓 이슈 → 이슈별 TDD·리뷰·PR)를 실제로 돌려 보는 실습 대상이다.

**성공의 모습:** 발표 당일, 처음 보는 계정으로 가입 → 대화 → 일기 초안 → 수정·테마 변경 → 저장 → 지난 일기 다시 보기까지 끊김 없이 시연된다.

## 2. 목표 / 비목표 / 반목표

**목표**
- 여러 사람이 각자 가입해 **자기 일기만** 쓰고 본다.
- 자유 서술형 대화 → Claude가 이어 묻기 → 일기 초안 → 사람이 수정.
- 테마 8개 이상, 한글 폰트 10개 이상, 서로 독립적으로 선택.
- Vercel에 배포되어 공개 URL로 접속 가능.

**비목표 (이번 범위 밖)**
- 공유·친구·댓글 등 소셜 기능
- 리치 텍스트 서식(굵게, 색 등), 이미지 첨부, 음성 입력
- 감정 통계·그래프, 알림/리마인더, 검색
- 모바일 앱 (반응형 웹으로 충분)
- 결제·요금제

**반목표 (동작해도 이러면 실패)**
- 다른 사용자의 일기가 어떤 경로로든 보인다.
- Claude API 키가 브라우저로 노출된다.
- 한 사용자가 API 비용을 무제한으로 쓸 수 있다.
- 대화가 지루할 만큼 길거나(7번 이상 질문), 재료가 없을 만큼 짧다(질문 3번 미만에서 강제 종료).
- 엔터프라이즈급으로 부풀어 발표 전에 못 끝난다.

## 3. 사용자 흐름

1. **가입/로그인** → 오늘 일기가 없으면 대화 화면, 있으면 오늘 일기 화면.
2. **대화**
   - 첫 질문은 고정: "오늘 하루는 어떠셨나요?" 사용자는 자유롭게 서술(선택지 버튼 없음).
   - Claude가 답을 읽고 감정·사건을 짚어 다음 질문 1개를 한다. 질문은 짧게, 한 번에 하나.
   - 진행 점(●●●○○)으로 대략의 위치를 보여 준다.
3. **일기 초안** → Claude가 대화 전체로 제목 + 본문 초안을 쓴다(1인칭, 사용자의 말투와 사실만 사용, 지어내지 않음).
4. **수정** → 제목·본문 텍스트 칸에서 직접 고친다. 테마·폰트를 고른다. 저장.
5. **지난 일기** → 날짜별 목록(또는 달력)에서 열람·수정. 각 일기 아래 대화 기록을 접어서 볼 수 있다.

## 4. 수용 기준 (번호 = 테스트 하나)

| # | 기준 |
|---|------|
| R1 | 첫 질문은 항상 "오늘 하루는 어떠셨나요?"이고 입력은 자유 텍스트다. |
| R2 | Claude의 후속 질문은 최소 3번, 최대 6번이다. 6번째 답 뒤에는 질문 없이 초안 단계로 간다. |
| R3 | 3번째 후속 질문 이후 Claude가 재료가 충분하다고 판단하면 마무리를 제안할 수 있다. |
| R4 | 3번째 후속 질문 이후 사용자는 언제든 [이제 일기 쓰기]로 초안 단계로 갈 수 있다. 그 전에는 버튼이 비활성이다. |
| R5 | 초안은 제목 + 본문이며, 사용자가 자유롭게 수정·저장할 수 있다. |
| R6 | 사용자당 **하루 1편**. 같은 날 새 대화를 시작할 수 없고, 그날 일기를 수정한다. "하루"의 기준은 사용자 브라우저의 로컬 날짜다. |
| R7 | 다른 사용자의 일기·대화는 API·DB 어느 경로로도 읽기·쓰기·삭제가 불가능하다 (Supabase RLS로 강제). |
| R8 | Claude API 키는 서버에만 있고 클라이언트 번들·응답에 나타나지 않는다. |
| R9 | 테마 ≥ 8개, 폰트 ≥ 10개. 테마와 폰트는 독립 선택이며 일기마다 저장된다. 새 일기는 마지막에 쓴 조합으로 시작한다. |
| R10 | 폰트는 선택된 것만 전체 로드한다. 목록 미리보기는 가벼운 방식(서브셋 등)으로 첫 화면을 느리게 만들지 않는다. |
| R11 | 지난 일기를 날짜순으로 열람·수정할 수 있고, 대화 기록을 접어서 볼 수 있다. |
| R12 | 탈퇴하면 그 사용자의 일기·대화가 모두 삭제된다. |
| R13 | 사용자당 하루 Claude 호출 수에 상한이 있다(대화 중 재시도 포함). 상한 초과 시 친절한 안내를 보여 준다. |
| R14 | Claude 호출이 실패하면 사용자가 쓴 답은 사라지지 않고, 다시 시도할 수 있다. |

## 5. 기술 구성 (결정됨)

**선택: A안 — Next.js + Supabase + Vercel**

| 영역 | 결정 |
|------|------|
| 언어/프레임워크 | TypeScript, Next.js (App Router). 화면과 서버 API가 한 프로젝트. |
| 인증 | Supabase Auth, **구글 로그인만** (이메일 가입 없음 → 시연 시 클릭 한 번 가입, 일회용 계정 남발 억제) |
| 계정 준비 | Supabase·Vercel·Anthropic API 키 모두 사용자에게 이미 있음. 새로 만들지 않고 연결만 한다. 도메인은 `*.vercel.app`. |
| DB | Supabase Postgres, 모든 사용자 테이블에 RLS (`user_id = auth.uid()`) |
| Claude 호출 | Next.js 서버 쪽(Route Handler 등)에서만, 공식 `@anthropic-ai/sdk`. 응답은 스트리밍으로 표시. |
| 모델 | 환경변수(예: `ANTHROPIC_MODEL`)로 지정. 사용자가 현재 쓰는 API로 테스트하므로 모델 선택은 깊게 다루지 않는다. |
| 배포 | Vercel |
| 스모크 테스트 | Playwright |

**검토한 대안**
- **B. Next.js + Auth.js + 일반 Postgres(Neon 등):** 업체 종속은 적지만, 사용자 분리를 앱 코드의 쿼리 조건에 의존한다. 하나만 빠뜨려도 노출 → R7을 구조로 보장하지 못해 탈락.
- **C. 프론트/백엔드 분리:** 계층은 깔끔하지만 프로젝트 2개·배포 2곳·CORS·토큰 전달로 2주 데모에 과하다. 탈락.

**선택 이유:** 2주 안에 배포까지 가능하고, 이 서비스의 최대 위험(남의 일기 노출)을 DB 구조(RLS)로 막는다 — 노트의 "지시문이 아니라 구조로 막는다" 원칙과 일치.

## 6. 데이터 (개략)

- `diaries`: id, user_id, date(사용자 로컬 날짜), title, body, theme_id, font_id, created_at, updated_at. `(user_id, date)` 유일.
- `diary_messages`: id, diary_id(또는 진행 중 세션 id), user_id, role(assistant/user), content, order, created_at.
- `profiles`(선택): user_id, last_theme_id, last_font_id.
- 사용량 상한(R13)을 위한 카운트 저장 방식은 빌더 재량.
- 모든 테이블 RLS 켬. 탈퇴 시 cascade 삭제(R12).

테마·폰트 목록은 DB가 아니라 **코드 안의 데이터 목록**(테마 = 색·배경 무늬·줄 간격 등의 CSS 변수 묶음, 폰트 = 이름·로드 주소). 추가는 목록에 한 줄.

## 7. 대화 규칙 (프롬프트 설계 방향)

- 질문은 짧게, 한 번에 하나, 공감 한 마디 + 질문.
- 사용자의 감정·사건을 구체적으로 짚는다("회의가 길어졌다고 하셨는데…").
- 상담·조언·판단을 하지 않는다. 일기 재료를 모으는 것이 목적.
- 질문 횟수 규칙(R2–R4)은 **서버 코드가 강제**한다. 모델이 "충분하다"고 판단하는 신호는 구조화된 출력(예: `{question, ready_to_write}`)으로 받는다. 프롬프트에만 의존하지 않는다.
- 초안은 사용자가 말한 사실만 사용하고, 1인칭 일기체로 쓴다.
- 사용자 입력은 데이터로 취급한다(프롬프트 인젝션으로 다른 사용자 데이터에 접근할 수 없음은 R7이 구조로 보장).

## 8. 테마·폰트

시안: `.superpowers/brainstorm/` 의 `themes.html` (사용자 확인 완료).

- 테마 8개: 크림 종이, 손글씨 다이어리(모눈), 밤하늘(다크), 미니멀 + 4개 추가(예: 벚꽃, 빈티지 편지지, 숲, 크라프트지 — 빌더가 최종 선정).
- 폰트 10개: 고운바탕, 나눔펜, Noto Serif KR, 고운돋움, 감자꽃, 하이멜로디 + 4개 추가(빌더가 Google Fonts 한글 폰트에서 선정, 라이선스 OFL 확인).
- "최대한 많이"가 사용자의 바람이므로, 추가가 목록 한 줄로 끝나는 구조가 필수.

## 9. 제약

- 발표일 2026-12-01까지 배포·시연 가능해야 함 (약 2주).
- 비밀값(API 키, Supabase service role key)은 환경변수로만, 저장소에 커밋 금지.
- 개발은 하네스 노트의 흐름을 따른다: ADR → 스펙 이슈 → 티켓 이슈 → 이슈별 테스트 먼저·리뷰·PR, 워크트리 → beta → main. 하네스 자체의 권한·멈춤 조건(ADR-0001)은 이 문서와 별도로 정한다.

## 10. 세부 결정 (설계 검토 후 Claude가 정함 — 사용자 확인 대상)

1. **일기 생성 시점과 이어 쓰기:** 첫 답을 보내는 순간 그날의 `diaries` 행을 `status = in_progress`로 만든다. 상태는 `in_progress → drafted → saved`. 대화 도중 나갔다 돌아오면 **이어서** 진행한다(R6 때문에 새로 시작은 없음). 질문 횟수는 서버가 저장된 `diary_messages`로 센다.
2. **날짜 신뢰:** 클라이언트가 로컬 날짜를 보내되, 서버는 서버 시각 기준 ±14시간(세계 시간대 범위) 안의 날짜만 받는다. 과거·미래 날짜로 새 일기를 만들 수 없다. 데모 수준에서 이 정도면 충분.
3. **비용 상한 두 겹:** 사용자당 하루 호출 상한(R13) + **서비스 전체 하루 호출 상한**(환경변수, 넘으면 새 대화 중단·안내). 일회용 계정을 여러 개 만들어 비용을 쓰는 경로를 막는다.
4. **스트리밍과 구조화 출력:** 질문 문장만 스트리밍해서 보여 주고, `ready_to_write` 같은 신호는 응답이 끝날 때 별도 필드로 받는다. 구체적인 방식(도구 호출, 구분자 등)은 빌더가 정한다.
5. **초안 호출은 상한에서 예약:** 사용자 상한을 계산할 때 초안 1회분을 항상 남겨 둔다. 그래도 초안 생성이 실패하면 빈 초안 화면을 보여 주고, 사용자가 직접 쓰거나 다시 시도할 수 있다.
6. **탈퇴:** 확인 단계(예: "탈퇴" 입력)를 거친 뒤 바로 영구 삭제한다. 내보내기는 없다. service role key는 이 서버 경로에서만 쓰고, 테스트를 따로 둔다.
7. **지난 일기:** 대화 기록은 읽기 전용이고, 초안을 다시 생성하는 기능은 없다. "마지막 테마·폰트"는 일기를 저장할 때마다 갱신한다.
8. **beta 환경:** beta 브랜치는 Vercel Preview 배포를 쓴다. Supabase는 데모 기간 동안 프로젝트 하나를 공유한다. 실제 사용자 데이터는 없는 전제다.
